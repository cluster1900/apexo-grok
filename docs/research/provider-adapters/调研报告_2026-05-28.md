# Provider Adapter crate 选型调研报告 — 2026-05-28

- **触发**：`docs/architecture/provider-and-model/架构设计.md` 将 Rust provider crate 选型列为未决问题；M1 Rust workspace skeleton 前需要确定 provider adapter 的依赖边界。
- **结论**：M1 默认不引入上层 LLM/agent 框架作为核心依赖。建议自建 `opencode-provider` 协议适配层，直接基于 `reqwest`、`tokio`、`serde`、`tracing`、`thiserror` 实现上游兼容 contract；Bedrock 可优先使用官方 `aws-sdk-bedrockruntime` / `aws-config`；`genai` 进入限时原型验证，不直接成为主路径；`rig-core`、`async-openai`、单 provider SDK 只作为参考或局部备选。

## 1. 问题陈述

本次调研回答三个问题：

1. Rust 迁移是否应直接采用现成多 provider crate 承接 opencode 的 provider/model 层？
2. 哪些 crate 满足许可证兼容、近 12 个月有维护、无已知直接 RustSec 高风险公告的底线？
3. M1 skeleton 应该以什么依赖边界启动，才能保留后续 OpenAI Responses、Anthropic Messages、Gemini、Bedrock Converse、OpenAI-compatible、Copilot、plugin provider 等上游行为？

## 2. 上游能力边界

上游 provider 层不是简单的 chat completion wrapper。当前源码和文档基线要求 Rust 版保留：

- bundled AI SDK provider：`@ai-sdk/openai`、`@ai-sdk/openai-compatible`、`@ai-sdk/anthropic`、`@ai-sdk/amazon-bedrock`、`@ai-sdk/azure`、`@ai-sdk/google`、`@ai-sdk/google-vertex`、`@openrouter/ai-sdk-provider`、`@ai-sdk/xai`、`@ai-sdk/mistral`、`@ai-sdk/groq`、`@ai-sdk/deepinfra`、`@ai-sdk/cerebras`、`@ai-sdk/cohere`、`@ai-sdk/gateway`、`@ai-sdk/togetherai`、`@ai-sdk/perplexity`、`@ai-sdk/vercel`、`@ai-sdk/alibaba`、GitLab、Copilot、Venice。
- protocol 级行为：OpenAI Chat、OpenAI Responses、Anthropic Messages、Gemini、Bedrock Converse、OpenAI-compatible streaming。
- opencode 特有行为：provider catalog 合并顺序、model variant、providerOptions namespace remap、SSE per-chunk timeout、context overflow 规则表、Copilot GPT-5 Responses API 路由、`gpt-5-chat-latest` alias 过滤、prompt cache 标记、usage/cost 调整、plugin provider transform。
- auth 行为：API key、OAuth、wellknown auth、`OPENCODE_AUTH_CONTENT` 覆盖、Bedrock/Vertex/Copilot/GitLab 等特殊认证。

因此选型标准不是“能发请求”，而是“能否不吞掉 opencode 的兼容 contract”。

## 3. 候选方案

### 3.1 自建 opencode provider adapter（推荐主路径）

以 `opencode-provider` crate 承接统一领域 contract，基础依赖只引入成熟底层 crate：

- HTTP/stream：`reqwest`
- async runtime：`tokio`
- schema：`serde`、`serde_json`
- error：`thiserror`
- observability：`tracing`
- Bedrock：官方 `aws-sdk-bedrockruntime`、`aws-config`

优点：

- 完全保留上游 opencode 的 providerOptions、message transform、error mapping、usage/cost、plugin provider 等行为。
- 可以把 OpenAI/Anthropic/Gemini/Bedrock/OpenAI-compatible 的协议 adapter 做成可测试的 Rust contract。
- 不把上层 agent、memory、vector store、prompt 编排框架引入 provider 层，符合 DDD 边界。

风险：

- 初期实现成本高，需要自己维护 streaming frame parser、schema transform 和 provider 特例。
- 需要用 recorded/golden fixtures 把行为锁住，否则容易漂移。

### 3.2 `genai`

`genai` 是目前覆盖面最接近上游 provider 范围的 Rust 多 provider crate。其 README 声明提供 native-protocol multi-provider API，并列出 OpenAI、OpenAI Responses、Anthropic、Gemini、Vertex、Bedrock、GitHub Copilot、OpenRouter、xAI、Groq、DeepSeek、Cohere、Together 等 provider。

适用点：

- 可作为 M1/M2 原型对照，快速验证多 provider streaming、tool calling、reasoning、prompt cache 等 Rust 表达方式。
- 可帮助比较 OpenAI Responses、Bedrock、Vertex、GitHub Copilot 的实现差异。

不建议直接作为主路径的原因：

- 它有自己的 model-to-adapter resolution、model alias、option 表达和 provider-neutral schema，可能与 opencode 的 catalog/filter/variant/providerOptions 规则冲突。
- opencode 需要精准复刻上游 `ProviderTransform`、Copilot 特殊路由、SSE timeout、context overflow 和 plugin provider transform；如果直接压到 `genai` 抽象下，兼容性缺口会变隐蔽。
- 版本仍在快速演进，适合原型和参考，不适合在 M1 锁死为核心边界。

### 3.3 `async-openai`

`async-openai` 是 OpenAI 专用 SDK，维护活跃，OpenAI API 覆盖较完整。

适用点：

- 可作为 OpenAI Chat/Responses API 类型参考。
- 如果后续 OpenAI adapter 维护成本过高，可考虑局部使用，但必须通过 opencode contract 包装。

不建议作为 M1 主依赖的原因：

- 只覆盖 OpenAI，不解决 Anthropic、Gemini、Bedrock、OpenRouter、Copilot、OpenAI-compatible 等主范围。
- opencode 对 OpenAI OAuth、Azure、Copilot Responses、providerOptions、usage 调整有特殊规则，仍需要外层大量定制。

### 3.4 `rig-core`

`rig-core` 是上层 LLM application / agent framework， provider 覆盖较广，生态活跃。

不建议进入 provider 核心的原因：

- 它包含 agentic workflow、embedding、vector store、memory 等上层抽象，和本仓库 DDD 中 provider/model 上下文边界不一致。
- README 明确提示未来更新可能有 breaking changes；作为 provider core 会放大升级风险。
- opencode-rs 已有自己的 agent/session/tool/permission 领域模型，不应引入第二套 agent 抽象。

### 3.5 SSE crate

上游要求 provider streaming 对 `text/event-stream` 做 per-chunk read timeout，并把 OpenAI/Anthropic/Gemini/Bedrock/OpenAI-compatible stream frame 归一化。

候选情况：

- `eventsource-client`：维护活跃、下载量高、Apache-2.0，但默认包含 EventSource 重连/指数退避语义，和 LLM 单次请求 stream 不完全一致；README 也提示 API 仍处早期。
- `eventsource-stream`、`reqwest-eventsource`：下载量高，但更新时间分别是 2022-02-17 和 2024-03-29，不满足本仓库“近 12 个月有维护”的新依赖要求。
- `sse-core` / `sse-frame` / `eventsrc`：维护时间满足，但生态和下载量太低，暂不建议作为核心依赖。

M1 建议先在 `opencode-provider` 内实现小型、私有、fixture 覆盖的 SSE frame parser，并把 parser fuzz target 列入测试计划；如果原型证明 `eventsource-client` 可禁用重连且支持 per-chunk timeout，再改为外部 crate。

## 4. 评估维度

| 维度 | 说明 |
|---|---|
| 上游兼容 | 是否能表达 opencode 的 providerOptions、message transform、error mapping、plugin provider、usage/cost。 |
| provider 覆盖 | 是否覆盖 OpenAI/Anthropic/Gemini/Bedrock/OpenAI-compatible/Copilot/OpenRouter 等核心面。 |
| 边界纯度 | 是否只做 provider/model，不把 agent、memory、vector store、prompt 编排塞进 provider 层。 |
| 维护性 | crates.io 最近更新时间、GitHub 最近 push、下载量和生态信号。 |
| 许可证 | MIT / Apache-2.0 兼容优先。 |
| 安全 | RustSec advisory-db 中是否存在直接 crate 命中；正式引入时仍需 `cargo audit` / `cargo deny check`。 |

## 6. 对比分析

| 方案 | 上游兼容 | provider 覆盖 | 边界纯度 | 维护 / 许可证 | 风险 |
|---|---|---|---|---|---|
| 自建 adapter + `reqwest` | 高；可逐条迁移上游规则 | 取决于实现排期 | 高 | `reqwest` 成熟、双许可证 | 实现量较大，必须有 recorded/golden/fuzz 测试。 |
| `genai` 主路径 | 中；覆盖面接近但抽象不同 | 高 | 中 | 活跃、双许可证 | 可能吞掉 opencode 特有 transform 和 route 规则。 |
| `async-openai` 主路径 | OpenAI 高，整体低 | 低 | 中 | 活跃、MIT | 只解决单 provider，会造成 provider 层碎片化。 |
| `rig-core` 主路径 | 中低 | 高 | 低 | 活跃、MIT | 引入 agent/memory/vector store 上层框架，冲突 DDD 边界。 |
| `eventsource-client` 处理 SSE | 中 | N/A | 中 | 活跃、Apache-2.0 | 默认重连语义不符合 LLM 单次 stream，需验证可控性。 |

关键判断：

- opencode-rs 的 provider 层是兼容性边界，不是通用聊天 SDK 边界。
- 现成多 provider crate 可以加速原型，但不能替代上游 contract 清单、OpenAPI/SDK schema、recorded fixtures。
- 单 provider SDK 会让每个 provider 的行为散落到外部 crate，反而降低 `ProviderTransform` 规则表的可审计性。

## 7. 决策与理由

### 决策

M1 采用 **自建 opencode provider adapter + 成熟基础 crate**：

```text
opencode-provider
├── domain-facing contract: ChatProviderPort / ProviderAuthPort / ModelCatalogPort
├── protocol adapters: openai_chat / openai_responses / anthropic_messages / gemini / bedrock_converse / openai_compatible
├── transform: providerOptions / message normalize / cache / context overflow / usage
├── transport: reqwest client / timeout / retry / tracing / secret redaction
└── test fixtures: recorded golden / stream parser / error parser / provider option snapshots
```

初始直接依赖建议：

- `reqwest`
- `tokio`
- `serde`
- `serde_json`
- `thiserror`
- `tracing`
- `aws-sdk-bedrockruntime`
- `aws-config`

暂不新增：

- `rig-core`
- `async-openai`
- `eventsource-stream`
- `reqwest-eventsource`

限时验证：

- 对 `genai` 做一个不进入主分支默认路径的原型：验证 OpenAI Responses、Anthropic Messages、Gemini、Bedrock、OpenRouter、Copilot 六类请求是否能保留 opencode 的 message/providerOptions/error/usage contract。原型通过前不把 `genai` 加入生产依赖。
- 对 `eventsource-client` 做一个小原型：验证是否能关闭/绕开 reconnect，并实现上游的 per-chunk read timeout。不能满足则保留内部 SSE parser。

### 为什么不直接选 `genai`

`genai` 覆盖广、维护新，是最值得验证的候选；但它的优势来自 provider-neutral 抽象和 model routing，而 opencode-rs 当前最重要的是上游兼容。直接采用会把差异藏进第三方抽象，后续排查 providerOptions、Copilot route、cache marker、usage token 调整会更难。

### 为什么不直接选 `rig-core`

`rig-core` 的边界超过 provider/model，上层 agent workflow 和本仓库已有 DDD 业务层重叠。把它放进 provider core 会引入第二套 agent 语义，违反当前架构分层目标。

### 为什么不直接选 `async-openai`

它只解决 OpenAI，无法回答 Anthropic/Gemini/Bedrock/Copilot/OpenRouter/plugin provider 的问题。M1 应先把 opencode 自己的协议 contract 做出来，而不是先绑定单 provider SDK。
