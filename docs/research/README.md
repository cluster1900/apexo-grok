# research/ 目录规范

收纳 **尚未收敛为设计** 的调研、对比、踩坑记录、上游源码阅读笔记。本目录的产物最终应推动 `architecture/` 或 `development/` 的更新；停留在本目录的文档视为"待消化"。

## 1. 适用场景

- 选型对比（候选 crate、模型、Provider、协议）。
- 上游 opencode（TS/Go 版）行为对齐：源码阅读 / 接口抓包 / 回放。
- 性能 / 内存 / 启动时间分析。
- 引入新依赖前的安全 & 维护性评估。
- Bug 根因调查（首次失败时归档，便于二次复现）。
- 大方向取舍未定时的脑暴记录。

## 2. 目录结构

```text
research/
├── README.md
└── <topic>/                   ← 按调研主题分子目录，英文小写短横线
    ├── 调研报告_YYYY-MM-DD.md  ← 主报告，命名带日期
    ├── 附件/                   ← 大块原始材料：抓包、profile、对比表
    └── 参考链接.md             ← 外部链接清单（可选）
```

- 单次小规模调研可直接放单文件 `<topic>_YYYY-MM-DD.md`，不必建子目录。
- 调研主题命名要让人一眼看懂："provider-streaming-protocol"、"tokio-vs-async-std"、"opencode-tool-permission-model"。

## 3. 调研报告模板

```markdown
# <主题> 调研报告 — YYYY-MM-DD

- **触发**：为什么要做这次调研（链接 Issue / 讨论）。
- **结论**：一句话写清结论与下一步动作。

## 1. 问题陈述
明确"我们要回答什么问题"。问题不清的调研是无效调研。

## 2. 候选方案 / 调研对象
列出对比的候选，每个候选有自己的小节。

## 3. 评估维度
列出本次评估关心哪些维度（性能 / 维护性 / 许可证 / 生态 / 与上游 opencode 行为一致性 / 学习成本 …）。

## 4. 对比分析
按维度交叉对比，给出原始数据（基准测试 / 代码片段 / 抓包）。

## 5. 决策与理由
明确选择，列出放弃其他方案的理由（"为什么没选 X"和"为什么选 Y"同样重要）。

## 6. 后续动作
- 是否需要更新 architecture/，更新哪些。
- 是否需要在 development/ 启动新功能，启动哪个。
- 是否需要开 ADR。
```

## 4. Bug 根因调查记录

Bug 排查记录建议命名 `bug-<简短描述>_YYYY-MM-DD.md`，必含：

- **复现路径**：完整可重放的步骤、输入、环境。
- **现象**：观测到的错误、日志、栈。
- **根因**：定位过程 + 最终根因。
- **修复**：链接修复 PR。
- **预防**：是否需要新增测试 / 监控 / lint 规则。

## 5. 时效与维护

- 调研一旦推动了 `architecture/` / `development/` 更新，相关结论以这两个目录的文档为准；本目录文档仅作为决策依据存在。
- 调研结论被后续调研推翻时，直接在新报告中说明并链接旧报告；不要去改旧报告的结论。
- 报告中的外部链接如失效，必须在文末追加"链接快照"段落（截图或关键引用），防止结论失去依据。
- 不再有任何价值（方向已废、对比对象已消失）的调研可直接删除，git 历史保留轨迹。
