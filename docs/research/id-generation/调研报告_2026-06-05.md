# ID 生成策略 调研报告 — 2026-06-05

- **触发**：M1 domain kernel 要求「零 I/O、零 runtime 依赖」，但 `SessionId` / `TurnId` / `MessageId` / `PartId` 在新建实体时必须铸造唯一 ID，内部 `TraceId` 缺失时也需要铸造；铸造需要随机源或时间。需确定铸造分层与底层方案，同时避免破坏外部 trace 复用。
- **结论**：**（待人工确认）** 分层已定：domain 只校验 / 重建（`TryFrom`），铸造由 application `IdFactory` 端口完成；M1 不引入任何 ID 依赖。底层倾向 **方案 A「复刻上游 opencode 方案」**（前缀 + 时间戳 + 单调计数 + base62 随机，可排序、与上游字符串形态一致，仅需一个 CSPRNG）；`ulid`（标准、有 uuid 互转）作为备选，`uuid` v7 作为次备选。最终方案需在 **M2 开工前**经人工确认。

## 1. 问题陈述

1. ID 铸造放在哪一层，才能既满足 domain 纯净，又能在 M4 持久化、M5 trace 贯穿时复用？
2. 底层用什么生成 ID 主体？要求：许可证兼容、近 12 个月有维护、无重大未修复 CVE、可选时间排序性、与上游 opencode ID 形态尽量一致。
3. ID 字符串形态（前缀 + 主体）如何定义，才能让值对象 `TryFrom` 稳定校验？

## 2. 候选方案 / 调研对象

### 2.1 分层方案

- A. domain 内直接生成（**否**：违反零 runtime 依赖、不可确定性测试）。
- B. application `IdFactory` + `Clock` 端口注入，domain 仅 `TryFrom`（**采纳**）。

### 2.2 ID 主体方案

- **A 复刻上游 opencode**：自实现「前缀 + 6 字节时间戳(hex) + base62 随机」，仅依赖一个 CSPRNG（`getrandom`/`rand`）+ `Clock`。
- **B `ulid`**：128-bit，Crockford base32（26 字符），时间有序，有 `uuid` 互转 feature。
- **C `uuid`（v7）**：标准 UUID，v7 时间有序；字符串为 36 字符 hex + 连字符。

## 3. 评估维度

许可证 / 维护活跃度 / RustSec 公告 / 时间排序性（利于 storage 索引与日志可读）/ 字符串形态与上游一致性 / 依赖足迹 / 确定性测试友好度（能否注入 fake）。

## 4. 对比分析

### 4.1 上游 opencode ID 形态（事实基准）

源码 `packages/opencode/src/id/id.ts`（sst/opencode）：

- 结构：`<prefix>_<12 hex 时间戳><14 字符 base62 随机>`，非前缀部分常量 `LENGTH = 26`。
- 前缀：`ses`(session)、`msg`(message)、`prt`(part)、`per`(permission) 等（注意：上游用 `prt`，且无 `turn`；本仓 `数据设计.md` 自定义为 `part_` 并新增 `turn_`，属本仓有意取舍，不在本报告变更范围）。
- 时间戳：`now = BigInt(ms) * 0x1000 + counter`，6 字节大端 hex；同毫秒内 `counter` 自增保证单调，跨毫秒归零。
- 排序：`descending` 时对 `now` 按位取反（`~now`），使新 ID 字典序在前。
- 示例：`ses_3cf7dd8d4ffeUPfENpVxfFojZ2`。

**结论：上游是自带的「前缀 + 时间 + 单调计数 + base62 随机」可排序方案，既非 UUID 也非 ULID 字符串形态。** 因此追求字符串级上游一致性时，只有「复刻上游」能完全对齐。

## 5. 决策与理由（待人工确认）

- **分层（已定）**：方案 B。`IdFactory` / `Clock` 为 application 端口；domain 值对象在 M1 只校验稳定 envelope（实体 ID 前缀 `ses_` / `turn_` / `msg_` / `part_`，存储辅助前缀 `ctx_` / `per_`，内部 trace 前缀 `trc_`，以及 body 字符集 / 长度范围），`TryFrom<&str>` 失败给字段定位错误。外部 trace id 走 W3C 32 hex / `traceparent` 校验并优先复用。理由：保持 domain 可独立、可确定性测试；M1 全程用固定字符串构造 ID，无需任何依赖；M2.0 再决定生成器主体是否收紧为上游 26 字符 body、ULID 或 UUID v7。
- **ID 主体（倾向，待拍板）**：
  - 首选 **方案 A 复刻上游**：唯一能做到字符串级上游一致，自带单调 + 可排序，便于 storage 索引与日志可读，新增依赖仅一个 CSPRNG。代价是需自写并测试铸造逻辑（含 base62、计数器、descending）。
  - 备选 **方案 B `ulid`**：标准、维护活跃、可与 `uuid` 互转；放弃字符串级上游一致，换取「不自实现随机/编码」。
  - 次备选 **方案 C `uuid` v7**：生态最广，但字符串最长且与上游差异最大。
- **放弃理由**：纯 `uuid` v4 无时间排序，不利于 storage 与日志，故 v4 仅作 v7 不可用时的回退，不单列。
