# progress/ 目录规范

记录每个功能 / 模块的 **真实当前状态**。本目录是冲突仲裁者：当 `architecture/` 或 `development/` 与代码描述不一致时，以代码和本目录为准。

## 1. 强制更新时机

下列事件发生即同 PR 更新本目录，否则任务不视为完成：

- 功能从"未开始"→"开发中"。
- 功能从"开发中"→"可用 / 已上线"。
- 范围调整（砍掉子功能、追加场景、降级方案启用）。
- 已知缺陷新增 / 修复 / 状态升级。
- 占位实现替换为真实实现。
- 依赖外部组件的状态变化（如某 Provider 接入完成 / 暂不可用）。

## 2. 目录结构

```text
progress/
├── README.md
├── overview.md              ← 全局态势板，按里程碑列出各功能状态（≥3 个功能后必维护）
└── <feature>/
    └── 功能现状.md           ← 与 development/<feature>/ 同名对齐
```

`<feature>` 名称必须与 `development/` 下的子目录一致，便于交叉跳转。

## 3. 功能现状.md 模板

每份文档必须包含以下字段（无内容时显式写"无"）：

```markdown
# <功能名> 功能现状

- **状态**：未开始 | 调研中 | 开发中 | 联调中 | 已上线 | 已下线
- **里程碑**：M1 / M2 / ...（与 overview.md 对齐）
- **责任人**：<负责人或团队>
- **最近更新**：YYYY-MM-DD

## 已交付能力
- 列出已实现且通过测试的能力，附 PR / commit 链接。

## 进行中
- 当前正在改的，含分支 / PR 链接。

## 待办
- 已规划但未动工的，按优先级排序。

## 已知缺陷
- 列出当前已知 bug / 限制 / 性能问题；每条需关联 Issue。

## 与设计的偏差
- 实现与 `development/<feature>/功能设计.md` 不一致的点，并标注是"已决定改设计"还是"待回填设计"。

## 风险与依赖
- 外部依赖、阻塞项、需上游协调的事项。
```

## 4. 写作纪律

- **不写历史叙事**：本目录是快照，不是日志。历史变更走 git 历史或 `development/<feature>/变更履历.md`。
- **不抄设计**：状态文档只回答"现在是什么样"，详细设计指向 `development/`。
- **不藏问题**：缺陷 / 偏差必须明示，缺失 = 失信。
- **避免一句话状态**："开发中"配数量化进展（已完成 N / 总 M、PR 链接），否则不可验收。

## 5. overview.md 维护

功能数量 ≥3 时必须维护：

- 按里程碑分组列出所有功能与状态。
- 每个功能一行，指向 `<feature>/功能现状.md`。
- 列出当前阻塞最多 / 风险最高的 3 项，置顶。

## 6. 功能移除

功能被永久移除时：直接删除对应子目录与 `overview.md` 中的引用。git 历史已经记录全过程，不保留占位文档。
