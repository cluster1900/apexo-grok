# Tool 执行与权限开发设计

## 1. 目标与非目标

- 目标：迁移内置 tool、tool registry、permission workflow、shell/patch/file/search/web/task/skill/question/todo、输出截断。
- 非目标：MCP/plugin tool 的 transport 细节。

## 2. 背景

上游入口：`tool/*`、`permission/*`、`shell/*`、`snapshot/*`、`patch/*`；测试入口：`test/tool/*`、`test/permission/*`。

## 3. 领域模型

| 聚合/对象 | 说明 |
|---|---|
| `ToolCall` | tool id、input、call id、status、result、metadata。 |
| `ToolDefinition` | schema、description、permission level、timeout、model filter。 |
| `PermissionWorkflow` | ask/allow/deny、patterns、pending、reply。 |
| `ToolOutput` | title、output、metadata、attachments、truncation。 |

## 4. 用例编排

- provider tool call -> schema 重校验 -> permission evaluate -> 执行 adapter -> 截断输出 -> 更新 part。
- shell -> argv 参数化 -> 审批 -> timeout/cancellation -> stdout/stderr 安全返回。
- file edit/apply_patch/write -> workspace guard -> snapshot -> patch -> event/file status。

## 5. 关键边界

- `ToolRegistryPort`、`ToolExecutor`、`PermissionPort`、`WorkspaceGuard`、`OutputTruncator`。
- 生产路径禁止 shell 字符串拼接；危险操作必须二次确认。

## 6. 错误模型

`ToolNotFound`、`ToolInputInvalid`、`PermissionDenied`、`WorkspaceViolation`、`ToolTimeout`、`ToolOutputTooLarge`、`PatchFailed`。

## 7. 测试与验收

- 18 个内置 tool schema 和行为 diff。
- path traversal、secret redaction、dangerous command、truncation、snapshot race。

## 8. 上游细节基线（2026-05-27 回补）

### 8.1 内置 Tool 完整清单

必须逐一建模并生成 schema/golden diff。registry 内部 id 基线：`invalid`、`shell`、`read`、`glob`、`grep`、`edit`、`write`、`task`、`fetch`、`todo`、`search`、`repo_clone`、`repo_overview`、`skill`、`patch`、`question`、`lsp`、`plan`。用户/协议展示别名基线：`shell`/`bash`、`webfetch`、`websearch`、`todo`/`todowrite`、`apply_patch`、`plan_exit`。`invalid` 是未知 tool fallback，不是普通用户可调用能力；`question`、`repo_clone`/`repo_overview`、`lsp`、`plan` 分别受 client/RuntimeFlags 条件控制。

### 8.2 Shell Arity 系统

`shell/permission/arity.ts` 的规则需要迁移为独立策略：按命令前缀和 token 数拆分命令，使 permission UI 能展示“人类可理解”的命令摘要。规则集约 150+ 条，Rust 版不得用简单字符串截断替代；新增规则必须有 fixture 覆盖。

### 8.3 External Directory Assertion

访问 workspace 外路径必须走 `external-directory.ts` 等价流程：解析目标路径 -> 判断是否在当前 instance context 内 -> 若越界则发起 `external_directory` permission -> metadata 携带 `filepath`、`parentDir` -> `always` pattern 只允许明确目录范围。拒绝后不得继续读写。

### 8.4 Tool Output Truncation

截断参数基线：

- `MAX_LINES = 2_000`
- `MAX_BYTES = 50 * 1024`
- `RETENTION = 7 days`
- 截断全文写入 `$DATA/tool-output/`，文件名使用 ascending tool id。
- 启动 1 分钟后开始清理，之后每小时清理过期截断文件。

截断提示必须区分普通工具和适合委派给 `explore` agent 的长输出。

### 8.5 Snapshot / Checkpoint

文件修改前必须接入 snapshot 机制。上游 `snapshot/index.ts` 使用独立 git repo 跟踪工作区快照，目录为 `$DATA/snapshot/{project.id}/{Hash.fast(worktree)}`，能力包括 `init`、`track`、`patch`、`restore`、`revert`、`diff`、`diffFull`、`cleanup`。基线限制：7 天 prune、单文件/patch 约 2MB 限制；revert/unrevert 依赖该机制。

### 8.6 Permission Reply 与 Always Pattern

permission 回复结构为 `once`、`always`、`reject`，可带 optional `message`。`ask`、`allow`、`deny` 只属于规则 action，不是人工回复值。`always` 可记录 patterns，使后续同类 tool call 自动通过；patterns 必须走 wildcard 匹配和最小范围校验。

### 8.7 MCP WebSearch 与 Plan Tool

`mcp-websearch.ts` 是特殊 MCP server 封装，向 tool registry 暴露 web search 能力；它需要纳入工具来源和权限链路，而不是被归到普通 provider tool。Plan 交互包含两个方向：`plan_enter` 是 build agent 进入 plan mode 的 permission/tool gate，`plan_exit` 是 plan agent 通过 `question` 交互确认切回 build agent 的 tool；两者都必须进入 tool schema、permission、agent permission matrix 和 transcript。

### 8.8 Patch Grammar / BOM / Wildcard

`apply_patch` 依赖独立 `patch/index.ts` grammar：`*** Begin Patch` / `*** End Patch` 包裹 add/delete/update hunk，update 支持 move、context chunk、EOF 标记和 verified parse。读写时必须保留 UTF-8 BOM：`Bom.split()` 读取、`Bom.join()` 写回、`Bom.syncFile()` 修正。permission pattern 使用 `util/wildcard.ts`，不能用 glob crate 直接替代。

Wildcard 匹配算法基线：

- 路径规范化：输入和 pattern 先将 `\` 全部替换为 `/`。
- 转义特殊 regex 字符后 `*` -> `.*`、`?` -> `.`。
- 末尾 `" *"`（空格加星号）特殊处理：该尾部变为可选组 `( .*)?`，使 `ls *` 同时匹配 `ls` 和 `ls -la`。
- 平台大小写：Windows（`win32`）使用 `si` flags（大小写不敏感），其他平台使用 `s` flags（大小写敏感）。
- `all(input, patterns)`：按 pattern 长度升序 + 字典序排列，最后命中的胜出（最长匹配优先语义）。
- `allStructured({ head, tail }, patterns)`：pattern 按空白拆分，head 匹配第一段，tail 使用 `matchSequence` 递归子序列匹配；`*` 段跳过（匹配零或多个 token）。

Rust 实现必须保留 `allStructured` 子序列语义（arity system 依赖此 API）和平台条件编译大小写行为。

### 8.9 Tool Definition 动态描述与参数自修复

tool definition 需要支持静态 description 和 `DynamicDescription = (agent: Agent.Info) => Effect<string>` 两种形式。registry 在向模型暴露 tool 前根据当前 agent 生成最终 description；`task` tool 需要列出当前 agent 可委派的 subagent，`skill` tool 需要列出当前可用 skill，这些都依赖动态描述。

LLM 调用参数不满足 schema 时，不应直接终止 session。上游会向模型返回固定格式的 `InvalidArgumentsError`：

```text
The <tool> tool was called with invalid arguments: <detail>.
Please rewrite the input so it satisfies the expected schema.
```

Rust 版必须保留该 self-repair 语义，让模型有机会重写参数；同时将 schema decode 失败纳入 tool part 状态和测试快照。

### 8.10 Model / Agent Tool Filter

`ToolRegistry.tools({ providerID, modelID, agent })` 同时按 provider、model 和 agent permission 过滤：

- `websearch` 只在 provider 能力和 RuntimeFlags 允许时暴露，例如 Exa/parallel provider 能力开关。
- GPT 系列且非 OSS、非 GPT-4 模型优先暴露 `apply_patch`，并隐藏 `edit` / `write`；其他模型保留 `edit` / `write` 并隐藏 `apply_patch`。
- agent permission 会过滤 `task` 可见 subagent、`skill` 可见 skill，以及 plan/question/repo tool 的可调用范围。
- plugin hook `tool.definition` 可调整最终 description/schema，但不能绕过权限、workspace guard 和 schema validation。若 hook 修改了 `parameters` 但未修改 `jsonSchema`，则丢弃 override 的 `jsonSchema`（防止 schema 与实际参数不一致）。

该过滤结果必须进入 provider request 的 tool list snapshot，不能只在执行阶段拒绝。

### 8.11 Custom Directory Tools

repo/local config directory 可加载自定义 TS/JS tool。上游没有单独的 `tools_dir` 字段，loader 从 `Config.directories()` 返回的配置目录集合扫描 tool 文件；目录来源包括 global config、项目祖先链中的 `.opencode`、home 下的 `.opencode`、以及 `OPENCODE_CONFIG_DIR`。

loader 基线：

- 加载前必须等待 config dependencies 就绪（`waitForDependencies()`），确保 config/plugin/provider 初始化完成后再扫描。
- 在每个 config directory 下扫描 `{tool,tools}/*.{js,ts}`，支持绝对路径、dotfile 和 symlink，但最终执行仍受 workspace guard 约束。
- 每个文件通过 dynamic import 加载；default export 使用文件 basename 作为 namespace，命名 export 使用 `<namespace>_<exportName>`。
- 参数 schema 使用 zod/json schema 或 legacy schema 归一化，执行前必须重新校验。
- 自定义 tool execute 获得受限 context：directory/worktree、permission ask bridge、truncation、logger、abort/cancellation。
- 输出必须走统一 truncation、permission、metadata 和 transcript 写入流程；失败不能破坏内置 tool registry。

### 8.12 Tool.Context 接口

tool 执行上下文必须完整传递给内置、MCP 和 custom tool：

| 字段 / 方法 | 语义 |
|---|---|
| `sessionID` | 当前 session。 |
| `messageID` | 当前 assistant message。 |
| `agent` | 当前 agent name。 |
| `abort` | tool cancellation signal。 |
| `callID?` | provider/tool call id。 |
| `messages` | 当前 filtered message history。 |
| `extra?` | 扩展上下文；session tool resolver 至少传 `model`、`bypassAgentCheck`、`promptOps`，read 入口还会使用 `bypassCwdCheck`。 |
| `metadata({ title?, metadata? })` | tool 运行中更新 running state 的 title/metadata，UI 和 transcript 依赖该回调展示进度。 |
| `ask(request)` | permission bridge；自动补 `sessionID`、tool call reference、agent/session permission merge 后进入 PermissionWorkflow。 |

`TaskTool` 依赖 `extra.promptOps` 创建 subtask prompt；`websearch` 依赖 `extra.model` 选择搜索模型名；`bypassAgentCheck` 只允许显式内部入口使用，不能暴露给普通 LLM tool 参数。

### 8.13 Shell Tool AST 解析与双重 Permission

Shell tool 不使用简单字符串分割，而是通过 `web-tree-sitter` 加载 `tree-sitter-bash` 和 `tree-sitter-powershell` WASM grammar 解析完整 AST。`collect()` 遍历 AST `command` 节点，对每个节点调用 `parts()` 提取 token，再通过 `pathArgs()` 识别文件路径参数。Rust 版必须用等价 AST parser（如 tree-sitter Rust binding），不能用 regex/split。

Shell tool 的 `ask()` 发起**两次**独立 permission 请求：

1. `external_directory` permission：扫描命令中所有越界路径参数，若存在则先请求目录级权限。
2. `shell` permission：对解析出的命令 pattern 请求 shell 执行权限。

两次 ask 均需通过才会执行。

### 8.14 Permission Reject 级联

`permission/index.ts` 中当一个 permission request 收到 `reject` 回复时，会**立即 reject 同一 session 中所有其他 pending permission requests**。这确保用户 deny 一次后不会被连续弹出多个确认框。Rust 版必须在 PermissionWorkflow 中实现 session-scoped reject 广播。

### 8.15 Shell 进程生命周期常量

| 常量 | 值 | 语义 |
|---|---|---|
| `SIGKILL_TIMEOUT_MS` | `200ms` | `killTree()` 发出 SIGTERM 后等待 200ms 升级为 SIGKILL。 |
| `forceKillAfter` | `3 seconds` | Effect ChildProcess 层面的强制杀死超时。 |

两者是不同层面的 kill 路径：`killTree` 用于 shell cancellation，`forceKillAfter` 用于 tool timeout。

Shell output streaming 使用 `maxBytes * 2` 的滚动 chunk ring buffer 限制内存占用（不是 `maxBytes`），最终输出再经过 `tail()` truncation 到 `maxBytes`。
