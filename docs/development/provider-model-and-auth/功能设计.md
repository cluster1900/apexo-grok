# Provider、Model 与认证开发设计

## 1. 目标与非目标

- 目标：迁移 provider catalog、model status/capability/cost、API key/OAuth、LLM streaming、provider error/timeout、usage/cost。
- 非目标：云端 billing 页面和 UI 表单实现。

## 2. 背景

上游入口：`provider/*`、`auth/*`、`account/*`、`session/llm.ts`、`packages/llm/*`、`packages/core/src/provider.ts`。

## 3. 领域模型

| 聚合/对象 | 说明 |
|---|---|
| `ProviderCatalog` | provider、model、capability、status、cost、source merge。 |
| `ProviderCredential` | env/API key/OAuth token 的 secret ref。 |
| `ModelProfile` | limits、tool support、reasoning、attachments、variants。 |
| `LlmRequest` | messages、tools、model、stream options、usage budget。 |

## 4. 用例编排

- load catalog -> merge models.dev/config/plugin/auth -> filter available models。
- authorize/callback/logout -> 校验 state/code -> 保存 secret ref -> 更新 account/provider。
- send request -> protocol adapter -> streaming frames -> usage/cost/error mapping。

## 5. 关键边界

- `ModelCatalogPort`、`ProviderAuthPort`、`ChatProviderPort`、`ProtocolAdapter`、`UsageRecorder`。
- provider body、headers、tokens 默认脱敏；错误保留 retryable/statusCode 摘要。

## 6. 错误模型

`ProviderNotFound`、`ModelNotFound`、`AuthRequired`、`OAuthStateInvalid`、`ProviderRateLimited`、`ProviderStreamInvalid`、`UsageBudgetExceeded`。

## 7. 测试与验收

- provider plugin tests、model status、header timeout、LLM native recorded/golden、usage/cost。
- `packages/llm` protocol tests 映射到 Rust contract。

## 8. 上游细节基线（2026-05-27 回补）

### 8.1 Retry 策略

`session/retry.ts` 必须作为 provider 层契约：

- `RETRY_INITIAL_DELAY = 2_000ms`
- `RETRY_BACKOFF_FACTOR = 2`
- 无 header 时 `RETRY_MAX_DELAY_NO_HEADERS = 30_000ms`
- 总 cap 为 `2_147_483_647ms`
- 优先解析 `retry-after-ms` 毫秒；其次解析 `retry-after` 秒；若不是数字则按 HTTP date 解析。
- 有 retry header 但无法解析时回退指数退避；无 header 时使用指数退避并受 30 秒上限约束。

`ContextOverflowError` 明确不重试，应交给 compaction/overflow 流程。5xx 即使 SDK 未标记 retryable 也视为可重试。

### 8.2 Usage Limit / Upsell Action

`FreeUsageLimitError` 返回 `Retryable.action`：`reason = "free_tier_limit"`、provider、title、message、label、`link = https://opencode.ai/go`。`GoUsageLimitError` 使用 `reason = "account_rate_limit"`，根据 response body 的 workspace/limitName 和 `retry-after` 生成 settings 链接。该结构回传到 `SessionStatus.retry.action` 展示。

### 8.3 Model Variant

session 可指定 `model.variant`，用于 A/B 模型切换和 provider catalog 中的 model variants。Rust 版 session、message、usage、OpenAPI 和 SDK 都必须保留该字段，不得只存 provider/model id。

### 8.4 LLM 双运行时

上游同时存在 `llm/ai-sdk.ts` 与 `llm/native-runtime.ts`。Rust 设计必须区分：

- AI SDK runtime：默认路径，复用 provider SDK、tool streaming、repair tool call。
- Native runtime：受 `experimentalNativeLlm` 控制，用原生 provider 协议，失败时回退 AI SDK。

Native runtime 支持条件（`status()` gate）：

| 维度 | 允许值 |
|---|---|
| provider ID | `openai`、`anthropic`、以 `opencode` 开头的 provider。 |
| npm package（`model.api.npm`）| `@ai-sdk/openai`、`@ai-sdk/openai-compatible`、`@ai-sdk/anthropic`。 |
| auth 方式 | API key（必须有值）；OAuth 仅当 provider 为 `openai` 且有 provider fetch override 时才允许。 |
| 返回类型 | `RuntimeStatus = "supported" { apiKey, baseURL? } \| "unsupported" { reason }`。 |

不满足上述任何一项时返回 `unsupported` 并附带原因，调用方回退到 AI SDK 路径。`baseURL` 仅当 `provider.options.baseURL` 为显式 string 时传递。

GitLab Workflow Language Model 使用 `gitlab-ai-provider`，是 provider runtime 的特殊集成点。

### 8.5 Provider Plugin 注入

plugin 可通过 catalog transform 注入 custom provider/model。merge 顺序必须记录来源：内置 catalog、models.dev、config、auth/account、plugin transform；plugin provider 需要 dedupe，不得覆盖 secret policy 和 unavailable model 过滤规则。

### 8.6 SSE Read Timeout

provider streaming response 必须实现上游 `wrapSSE()` 等价机制：仅对 `content-type: text/event-stream` 的响应包裹 per-chunk read timeout，默认 `OPENAI_HEADER_TIMEOUT_DEFAULT = 10_000ms`。任一 chunk 超过 timeout 未返回时，必须 abort 当前请求并取消 reader，错误归类为 provider stream timeout，避免长时间挂起占用 runner。

该 timeout 是每个 SSE chunk 的读超时，不是整次请求总时长；与 retry 策略结合时仍需遵守 context overflow 不重试。

### 8.7 Copilot Responses API 路由

GitHub Copilot provider 对 GPT-5+ 模型有特殊路由：`shouldUseCopilotResponsesApi(modelID)` 在模型 id 匹配 `gpt-<major>` 且 major >= 5、同时不是 `gpt-5-mini` 时，使用 Responses API；否则使用 Chat Completions。该选择影响 tool calling、reasoning content、stream frame 和 usage 解析，必须进入 provider adapter contract tests。

catalog 过滤还必须删除会与内置特殊路由冲突的 chat alias：当 provider 是 OpenAI、GitHub Copilot 或 OpenRouter 时，移除 `gpt-5-chat-latest`；当 OpenRouter model id 为 `openai/gpt-5-chat` 时也移除。custom provider 可以保留自己的同名 alias。

### 8.8 Provider SDK Key 与 Surrogate Sanitization

`provider/transform.ts` 的 `sdkKey()` 是 AI SDK `providerOptions` namespace 映射，不可省略：

| npm package | providerOptions key |
|---|---|
| `@ai-sdk/github-copilot` | `copilot` |
| `@ai-sdk/azure` | `azure` |
| `@ai-sdk/openai` | `openai` |
| `@ai-sdk/amazon-bedrock` | `bedrock` |
| `@ai-sdk/anthropic` / `@ai-sdk/google-vertex/anthropic` | `anthropic` |
| `@ai-sdk/google-vertex` | `vertex` |
| `@ai-sdk/google` | `google` |
| `@ai-sdk/gateway` | `gateway` |
| `@openrouter/ai-sdk-provider` | `openrouter` |
| `ai-gateway-provider` | `openaiCompatible` |

provider request 前必须执行 `sanitizeSurrogates()`，把孤立 UTF-16 surrogate code point 替换为 `U+FFFD`，避免 provider SDK 或 JSON 序列化在异常 Unicode 输入上失败。

`ProviderTransform.providerOptions()` 还包含特殊路由规则：

- Azure 同时写入 `openai` 和 `azure` namespace，因为 Azure Chat 与 Responses 路径读取的 providerOptions key 不同。
- Gateway provider 将 `gateway` 原样作为 gateway-native routing/caching 配置；其他 top-level options 按模型 id 前缀路由到 upstream slug，例如 `amazon/*` 映射到 `bedrock`。
- `@ai-sdk/openai-compatible`、`@ai-sdk/openai`、`@ai-sdk/anthropic` 在无明确 `sdkKey()` 时按 provider id 的点号前缀写入，例如 `wafer.ai` 写到 `wafer`。

### 8.9 Provider Error / Context Overflow Patterns

context overflow 不只靠 token budget 判定。`provider/error.ts` 的 provider error parser 必须迁移为规则表：

| Pattern / 条件 | 覆盖场景 |
|---|---|
| `prompt is too long` | Anthropic。 |
| `input is too long for requested model` | Amazon Bedrock。 |
| `exceeds the context window` | OpenAI Completions / Responses。 |
| `input token count.*exceeds the maximum` | Google Gemini。 |
| `maximum prompt length is \\d+` | xAI / Grok。 |
| `reduce the length of the messages` | Groq。 |
| `maximum context length is \\d+ tokens` | OpenRouter、DeepSeek、vLLM。 |
| `exceeds the limit of \\d+` | GitHub Copilot。 |
| `exceeds the available context size` | llama.cpp server。 |
| `greater than the context length` | LM Studio。 |
| `context window exceeds limit` | MiniMax。 |
| `exceeded model token limit` | Kimi For Coding、Moonshot。 |
| `context[_ ]length[_ ]exceeded` | generic fallback。 |
| `request entity too large` | HTTP 413 文本。 |
| `context length is only \\d+ tokens` | vLLM。 |
| `input length.*exceeds.*context length` | vLLM。 |
| `prompt too long; exceeded (?:max )?context length` | Ollama。 |
| `too large for model with \\d+ maximum context length` | Mistral。 |
| `model_context_window_exceeded` | z.ai 非标准 finish_reason 文本。 |
| `^4(00|13) ... (no body)` | Cerebras / Mistral 常见无 body 400/413。 |
| `statusCode === 413` 或 body error code `context_length_exceeded` | provider/status 兜底。 |

`parseStreamError()` 还需处理 streaming error body：`context_length_exceeded` -> `ContextOverflowError`；`insufficient_quota`、`usage_not_included`、`invalid_prompt` -> 不可重试 API error；`server_is_overloaded`、`server_error` -> 可重试 API error。OpenAI provider 的 404 可被视为 retryable，其余 provider 使用 SDK `isRetryable`。

### 8.10 LLM 参数规则

`ProviderTransform.temperature/topP/topK/options/smallOptions` 必须作为 provider contract，而不是散落在调用处。

| 函数 | 规则 |
|---|---|
| `temperature(model)` | Qwen -> `0.55`；Claude -> `undefined`；Gemini / GLM 4.6 / GLM 4.7 / MiniMax M2 -> `1.0`；Kimi K2 thinking/K2.5/K2P/K2-5 -> `1.0`，其他 Kimi K2 -> `0.6`。 |
| `topP(model)` | Qwen -> `1`；MiniMax M2 / Gemini / Kimi K2.5/K2P5/K2-5 -> `0.95`。 |
| `topK(model)` | MiniMax M2 变体 M2./M25/M21 -> `40`，其他 MiniMax M2 -> `20`；Gemini -> `64`。 |
| `smallOptions(model)` | 默认取第一个 variant；OpenAI/OpenAI package/Copilot 合并 `{ store: false }`；OpenRouter/LLM gateway Google 且无 small variant 时禁用 reasoning；Venice 无 small variant 时设置 `disableThinking`。 |

`options(input)` 基线：

- Anthropic package 的非 Claude 路径、Google Vertex Anthropic：`toolStreaming = false`。
- OpenAI provider、OpenAI package、GitHub Copilot：默认 `store = false`。
- Azure：`store = false` 且 `promptCacheKey = sessionID`。
- OpenRouter / LLM gateway：`usage.include = true`；Gemini 3 加 `reasoning.effort = high`。
- Baseten 或 opencode 上的 `kimi-k2-thinking` / `glm-4.6`：`chat_template_args.enable_thinking = true`。
- z.ai / zhipuai OpenAI-compatible：`thinking { type: enabled, clear_thinking: false }`。
- OpenAI 或显式 `setCacheKey`：`promptCacheKey = sessionID`。
- Google / Vertex reasoning model：`thinkingConfig.includeThoughts = true`；Gemini 3 加 `thinkingLevel = high`。
- Anthropic/Kimi K2P/Kimi K2.x：启用 thinking，budget 为 `min(16_000, floor(output_limit / 2 - 1))`。
- Alibaba-CN OpenAI-compatible reasoning model：`enable_thinking = true`，但排除 `kimi-k2-thinking`。
- Azure GPT-5.5：只设置 `reasoningSummary = auto` 并提前返回。
- 非 chat GPT-5：默认 `reasoningEffort = medium`、`reasoningSummary = auto`；OpenAI package 加 `include = ["reasoning.encrypted_content"]`。
- GPT-5.x 非 codex/非 chat/非 Azure：`textVerbosity = low`。
- opencode provider 上的 GPT-5：设置 `promptCacheKey`、encrypted reasoning include、`reasoningSummary = auto`。
- Venice：`promptCacheKey = sessionID`；OpenRouter：`prompt_cache_key = sessionID`；Gateway：`gateway.caching = auto`。

### 8.11 Message Transform Pipeline

`ProviderTransform.message()` 是 provider 请求前的消息预处理管道，顺序必须保持：

1. `unsupportedParts()`：user file/image 不被模型 modality 支持时，替换为可见错误文本；空 base64 image 替换为 corrupted image 错误文本。
2. `normalizeMessages()`：先清理孤立 UTF-16 surrogate，再按 provider 修正消息形态。
3. 对 Anthropic / Claude / Google Vertex Anthropic / Alibaba 等支持 cache control 的 provider 调用 `applyCaching()`。
4. 最后按 `sdkKey()` remap `providerOptions` key。

`normalizeMessages()` provider 特例：

- Anthropic：移除空 string message、空 text/reasoning part；保留带 signature/redactedData 的 reasoning。
- Bedrock：同样移除空 content，并保留 Bedrock signature/redactedData。
- Claude id：tool call/result id scrub 为 `[a-zA-Z0-9_-]`。
- Anthropic / Google Vertex Anthropic：assistant 中 tool-call 后跟非 tool content 时拆成 text message + tool-call message，避免 provider 拒绝顺序。
- Mistral / Devstral：tool id 去非字母数字、截断/填充到 9 字符；tool message 后接 user message 时插入 synthetic assistant text `Done.`。
- DeepSeek：assistant 缺 reasoning 时补空 reasoning。
- `capabilities.interleaved`：当模型声明 interleaved field 且 provider 不是 OpenRouter 时，从 assistant content 中移除 reasoning parts，把 reasoning text 拼接后写入 `providerOptions.openaiCompatible[reasoning_content|reasoning_details]`；即使 reasoning 为空也写回，支持 DeepSeek 等模型的空 reasoning 回放。

`applyCaching()` 规则：取前 2 个 system message 和最后 2 个 non-system message；Anthropic/Bedrock 走 message-level providerOptions，其他优先写最后一个 content part；providerOptions 同时覆盖 anthropic/openrouter/bedrock/openaiCompatible/copilot/alibaba 的 cache 标记。

### 8.12 Auth 三类型与环境变量覆盖

`Auth.Info` 是三元 discriminated union，不只是 API key + OAuth：

| type | 字段 | 语义 |
|---|---|---|
| `api` | `key` | 直接 API key 认证。 |
| `oauth` | `token`、`refresh_token?`、`expires_at?` | OAuth 2.0 流程。 |
| `wellknown` | `key`、`token` | well-known provider 的预共享凭据（如 opencode 自有 provider）。 |

`OPENCODE_AUTH_CONTENT` 环境变量：若存在，整个 auth store 从该 env var 反序列化（JSON），跳过 `auth.json` 文件读取。用于 CI/容器部署。

### 8.13 LLM Request 特殊路由

`llm/request.ts` 中有几个关键行为 provider doc 必须保留：

- **OpenAI + OAuth**：当 provider 为 `openai` 且 auth type 为 `oauth` 时，system prompt 不作为 system message 发送，而是写入 `options.instructions` 字段，messages 数组排除 system 消息。
- **Copilot `_noop` sentinel tool**：当 GitHub Copilot provider 的 tool list 为空但历史消息中包含 tool calls 时，注入 `_noop` sentinel tool 满足 API 要求。
- **opencode provider headers**：opencode-namespaced providers 发送 `x-opencode-project`、`x-opencode-session`、`x-opencode-request`、`x-opencode-client`。其他 providers 发送 `x-session-affinity` 和可选 `x-parent-session-id`。

### 8.14 Model Sort Priority 与 Small Model Fallback

默认 model sort priority（决定 UI 中模型展示顺序和默认选择）：`["gpt-5", "claude-sonnet-4", "big-pickle", "gemini-3-pro"]`。

`getSmallModel` fallback 优先列表：`claude-haiku-4-5` → `3-5-haiku` → `gemini-3-flash` → `gpt-5-nano`；`opencode` provider 和 `github-copilot` provider 有各自的 small model override。该列表影响 compaction/title/summary agent 使用的模型选择。

### 8.15 Usage Token 调整

`getUsage()` 中 `adjustedInputTokens = inputTokens - cacheReadInputTokens - cacheWriteInputTokens`，因为 AI SDK v6 的 `inputTokens` 已包含 cached tokens。cost 计算必须使用调整后的值。Bedrock 和 Venice 的 `cacheWriteInputTokens` 从 provider metadata 中额外提取。

### 8.16 M1 Rust crate 边界 — 2026-05-28

Provider Adapter crate 选型调研结论见 `docs/research/provider-adapters/调研报告_2026-05-28.md`。M1 skeleton 采用下列边界：

| crate | 层 | 职责 |
|---|---|---|
| `opencode_domain` | domain | ProviderId、ModelId、SessionId 等值对象；零 I/O、零 runtime 依赖。 |
| `opencode_application` | application | `ChatProviderPort`、provider request/response、provider error、`ProviderRegistry`；只定义 orchestration contract 和 provider 路由。 |
| `opencode_provider` | infrastructure | 基于 `reqwest` 的 provider transport 和后续 OpenAI/Anthropic/Gemini/Bedrock/OpenAI-compatible adapters。 |
| `opencode_server` | interface | M1 health contract；真实 HTTP router 等 OpenAPI/workspace routing 固定后再引入。 |

依赖方向固定为 `opencode_server -> opencode_application -> opencode_domain`，`opencode_provider -> opencode_application/opencode_domain`。`opencode_domain` 禁止依赖 `tokio`、HTTP、文件系统、数据库或 provider SDK。

M1 不把 `genai`、`rig-core`、`async-openai` 放进生产依赖；`genai` 和 `eventsource-client` 只进入原型验证清单。真实 provider protocol adapter 必须先补 recorded/golden fixture，再实现 OpenAI Chat / Responses、Anthropic Messages、Gemini、Bedrock Converse 和 OpenAI-compatible。

### 8.17 M1 Mock Provider 垂直链路 — 2026-05-28

`opencode_application::ProviderRegistry` 是 M1 的第一条可测试 provider 垂直链路：调用方提交带 `ProviderId` 的 `ChatRequest`，registry 查找已注册 `ChatProviderPort`，成功时返回 `ChatResponse`，缺失时返回 `ProviderError::ProviderNotFound`。该链路不访问网络、不引入真实 protocol adapter，用于先固定 application 层路由语义和 mock provider 测试入口。

真实 provider adapter 后续接入时必须复用该 port，不允许 infrastructure DTO 泄漏到 application/domain。
