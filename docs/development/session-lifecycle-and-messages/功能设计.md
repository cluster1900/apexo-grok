# Session 生命周期与消息开发设计

## 1. 目标与非目标

- 目标：迁移 session CRUD、fork/children/archive/delete、message/part 状态机、prompt/run state、retry、revert、structured output、question 交互。
- 非目标：provider 具体协议、tool 具体执行、Web UI 展示细节。

## 2. 背景

上游入口：`packages/opencode/src/session/*`、`question/*`、`background/job.ts`；测试入口：`test/session/*`、`test/question/*`、`test/server/session-*`。

## 3. 领域模型

| 聚合/对象 | 说明 |
|---|---|
| `Session` | session info、parent/child、archive/share/revert、runner 状态。 |
| `Message` / `Part` | user/assistant 消息和 text/reasoning/file/tool/step/subtask part。 |
| `QuestionWorkflow` | structured question ask/answer/pending 状态。 |
| `RunState` | busy/idle/abort/retry/doom-loop 运行状态。 |

## 4. 用例编排

- 创建 session -> 解析 project/workspace/directory -> 初始化 system/user message。
- prompt -> 写 user message -> 启动 runner -> 处理 assistant stream 和 tool part -> 持久化事件。
- revert/compact/retry -> 校验 session 状态 -> 生成新 message/part 或状态标记 -> 发布 SSE。
- question ask/answer -> 创建 pending question -> 接收 answer -> 恢复 runner。

## 5. 关键边界

- `SessionRepository`、`MessageRepository`、`PartRepository`、`QuestionPort`。
- session domain 不直接调用 provider/tool/storage；application 只通过 port 编排。

## 6. 错误模型

`SessionNotFound`、`SessionBusy`、`MessageNotFound`、`InvalidPartState`、`QuestionExpired`、`AbortRequested`、`StorageFailure`。

## 7. 测试与验收

- message/part 状态机、分页、structured output、revert/compact/retry、abort、busy。
- HTTP session/message/question endpoint contract。
- prompt-to-tool-loop 场景与 SSE 事件顺序。

## 8. 上游细节基线（2026-05-27 回补）

以下内容必须进入本功能的 Rust 领域模型和接口验收，不能只停留在总方案：

### 8.1 SessionStatus 聚合

`SessionStatus` 独立建模，不能仅用泛化的 `RunState` 覆盖。

| 状态 | 字段 | 语义 |
|---|---|---|
| `idle` | `status` | session 当前无运行中的 agent loop。 |
| `busy` | `status` | session 正在处理 prompt、tool result、retry、compaction 或恢复任务。 |
| `retry` | `status`、`attempt`、`message`、`next`、`action?` | provider 请求可重试，UI/CLI 必须展示重试说明和下一次重试时间。 |

`retry.action` 字段基线：`reason`、`provider`、`title`、`message`、`label`、`link?`。`FreeUsageLimitError`、Go quota、rate limit 等场景依赖该结构展示 upsell 或设置入口。

### 8.2 Session 关键字段

`Session` 表和领域对象必须包含：`id`、`slug`、`projectID`、`workspaceID`、`directory`、`path`、`parentID?`、`summary?`、`cost`、`tokens`、`share?`、`title`、`agent`、`model.providerID`、`model.modelID`、`model.variant?`、`version`、`revert?`、`permission`、`time.created`、`time.updated`、`time.compacting?`、`time.archived?`。其中 `path` 是相对 worktree 的规范化路径，使用 `/` 分隔，是 session 列表过滤和 HTTP routing 的关键字段。

`summary` 子 schema：`{ additions: number, deletions: number, files: number, diffs: FileDiff[] }`。`diffs` 引用 `Snapshot.FileDiff`，revert diff 事件依赖该结构。

`revert` 子 schema：`{ messageID: MessageID, partID?: PartID, snapshot?: string, diff?: string }`。revert/unrevert round-trip 必须完整保留这四个字段。

时间字段约束：

- `time.compacting` 是 compaction 正在进行的非负毫秒时间戳标记，可被置空。
- `time.archived` 是归档时间戳；上游为兼容 legacy HTTP 接口允许有限负数，因此 Rust schema 不能只接受非负整数，但必须拒绝 NaN/Infinity 等不可 JSON 往返的值。

### 8.3 Context Window / Overflow

必须实现上游 `overflow.ts` 的判定口径：

- 可用输入窗口优先使用 `model.limit.input - reserved`；没有 input limit 时使用 `model.limit.context - maxOutputTokens`。
- `reserved = config.compaction.reserved ?? min(20_000, maxOutputTokens)`。
- `COMPACTION_BUFFER = 20_000`，`usable()` 结果需要扣除 buffer。
- `isOverflow()` 在 `config.compaction.auto === false` 或 context limit 为 0 时返回 false。
- token 计数使用 `total`，无 `total` 时使用 `input + output + cache.read + cache.write`。
- overflow 后进入自动 compaction，而不是把错误交给 provider retry。

### 8.4 Fork 命名规则

`getForkedTitle()` 必须保持上游规则：若 title 已以 ` (fork #n)` 结尾，则 fork 编号递增；否则追加 ` (fork #1)`。该规则影响 UI 标题、历史搜索和分叉 session 可读性。

### 8.5 Doom Loop 阈值

`DOOM_LOOP_THRESHOLD = 3`。当同一 assistant message 最近 3 个 tool part 的 `tool` 名称相同、输入 JSON 相同、且状态都不再是 `pending` 时，触发 `permission = "doom_loop"`；典型表现是同一 tool call 连续被拒绝或无法推进 3 次。permission 请求的 patterns/always 使用 tool 名称，避免 agent loop 无限重试。

### 8.6 Revert / Unrevert / Cleanup

`revert` 不是单步撤销，必须拆成三类 use case：

- `revert`：断言 session 非 busy，恢复已有 snapshot，收集目标 message 之后的 patch/file 变化，计算 diff summary，写入 `session_diff`，设置 `session.revert` 标记并发布 diff 事件。
- `unrevert`：基于 snapshot 恢复 revert 前的工作区状态，清除 `session.revert`。
- `cleanup`：删除 revert 点之后的 message/part/临时状态，并清理 snapshot/revert 标记。

### 8.7 PromptInput 与 Structured Output

`SessionPrompt.prompt()` 的输入不能简化为纯文本。`PromptInput` 字段基线：

| 字段 | 语义 |
|---|---|
| `sessionID` | 目标 session。 |
| `messageID?` | 调用方指定 user message id。 |
| `model?` | 本次 prompt 覆盖模型。 |
| `agent?` | 本次 prompt 覆盖 agent。 |
| `noReply?` | 只写入 user message，不启动 assistant 回复，供内部流程和 transcript 写入使用。 |
| `tools?` | deprecated 字段，仅用于兼容旧调用。 |
| `format?` | 输出格式；`json_schema` 触发 structured output tool。 |
| `system?` | 覆盖或追加本次 system prompt。 |
| `variant?` | 本次模型 variant。 |
| `parts[]` | text/file/agent/subtask 等 user part。 |

当 `format.type = "json_schema"` 时，prompt 组装必须自动注入 `StructuredOutputTool` 和专用 system prompt，并将 tool choice 设为 required，使模型必须通过该 tool 返回结构化数据。tool 返回成功后写入 `message.structured`；若 assistant 完成但没有得到结构化输出，则抛出 `StructuredOutputError`，错误中保留失败消息和 retry 次数。该机制属于 session prompt 主链路，不是普通 tool registry 的可选扩展。

### 8.8 Shell Prompt 入口

`SessionPrompt.shell()` 是独立入口：用户输入 `!command` 时直接执行 shell，不进入 LLM agent loop，也不同于 assistant 调用 `shell` tool。

执行基线：

- 先创建 user message 和 synthetic text part，说明该 tool 由用户触发。
- 创建 assistant tool part，tool id 使用 shell tool，对应命令、cwd、env 和输出状态都进入 transcript。
- 通过 runner 的 ready latch 连接 UI 状态，确保 shell 开始后调用方能感知 busy/shell 状态。
- 使用 `Shell.preferred()` / `Shell.args()` 构造命令参数，禁止把该入口误实现成 provider tool call。
- 执行前触发 plugin hook `shell.env`，合并插件返回的环境变量，并固定 `TERM=dumb`。

### 8.9 Command Prompt 入口

`SessionPrompt.command()` 处理 slash command 模板，是第三条 prompt 入口。

模板替换基线：

- `CommandInput` 包含 `sessionID`、`messageID?`、`agent?`、`model?`、`arguments`、`command`、`variant?`、`parts?`。
- `$1`、`$2` 等 positional 占位符按用户 arguments 替换；最后一个 positional 可消费剩余参数。
- `$ARGUMENTS` 替换为完整 arguments；模板没有 positional 占位符但用户传了 arguments 时，arguments 追加到模板末尾。
- `@file` 引用通过 ConfigMarkdown/file part 解析进入 prompt parts，必须走 workspace guard 和 instruction 注入规则。
- ``!`command` `` shell 片段先执行并把输出替换回模板，执行使用 preferred shell 和当前 cwd，输出进入不可信输入处理链。

### 8.10 Message Part Schema 基线

`MessageV2.Part` 是 12 种 tagged union，Rust enum 必须逐项建模并保留公共 `id`、`messageID`、`sessionID`。

| Part | 关键字段 |
|---|---|
| `text` | `text`、`synthetic?`、`ignored?`、`time? { start, end? }`、`metadata?`。 |
| `reasoning` | `text`、`metadata?`、`time { start, end? }`；`time` 必填。 |
| `file` | `mime`、`filename?`、`url`、`source?`；`source` union 为 `file { path, text }`、`symbol { path, range, name, kind, text }`、`resource { clientName, uri, text }`。 |
| `tool` | `callID`、`tool`、`state`、顶层 `metadata?`；顶层 metadata 与 `state.metadata` 分开保存。 |
| `step-start` | `snapshot?`。 |
| `step-finish` | `reason`、`snapshot?`、`cost`、`tokens { total?, input, output, reasoning, cache { read, write } }`。 |
| `compaction` | `auto`、`overflow?`、`tail_start_id?`。 |
| `subtask` | `prompt`、`description`、`agent`、`model? { providerID, modelID }`、`command?`。 |
| `retry` | `attempt`、`error: APIError`、`time { created }`。 |
| `snapshot` | `snapshot`。 |
| `patch` | `hash`、`files[]`。 |
| `agent` | `name`、`source? { value, start, end }`。 |

`ToolPart.state` 也必须按 union 建模：

| State | 字段 |
|---|---|
| `pending` | `input`、`raw`。 |
| `running` | `input`、`title?`、`metadata?`、`time { start }`。 |
| `completed` | `input`、`output`、`title`、`metadata`、`time { start, end, compacted? }`、`attachments? FilePart[]`。 |
| `error` | `input`、`error`、`metadata?`、`time { start, end }`。 |

### 8.11 Assistant Message Schema 基线

`AssistantMessage` 字段不能只从 legacy message 表推导。Rust 领域对象和 storage projection 必须包含：

| 字段 | 语义 |
|---|---|
| `id`、`sessionID`、`role = "assistant"` | message identity。 |
| `time { created, completed? }` | assistant 创建和完成时间。 |
| `error?` | `AssistantErrorSchema`，由 `fromError()` 映射。 |
| `parentID` | 对应 user message id。 |
| `modelID`、`providerID`、`variant?` | 实际请求的模型与 variant。 |
| `mode` | deprecated 字段，仍需兼容读取。 |
| `agent` | 生成该 assistant 的 agent。 |
| `path { cwd, root }` | 当前工作目录与 workspace/worktree root，Rust 中应建模为路径值对象。 |
| `summary?` | compaction summary assistant 标记；影响 tool 禁用、filterCompacted 和 summary 流程。 |
| `cost` | 本 assistant 累计 cost。 |
| `tokens { total?, input, output, reasoning, cache { read, write } }` | usage 聚合。 |
| `structured?` | structured output 结果。 |
| `finish?` | provider finish reason，例如 tool-calls、stop、error。 |

### 8.12 toModelMessages 转换管道

`MessageV2.toModelMessagesEffect()` 是 session -> provider 的核心转换，必须有独立 contract tests：

- 空 parts 的 message 跳过。
- user text part 只转发非 ignored 且非空文本；text/plain 和 directory file 不作为 file 转发。
- user media 在 `stripMedia` 时转成 `[Attached <mime>: <filename>]` 文本；普通 file 转为 provider file part。
- user `compaction` part 转为“询问目前进展”的文本；`subtask` part 转为“用户执行了工具”的合成文本。
- assistant 带 error 时跳过；例外是 `AbortedError` 且存在 step-start/reasoning 以外的实质 part，此时保留可回放内容。
- assistant 空 text 遇到 signed reasoning 时转为单空格，避免 Anthropic 签名 reasoning 的相对位置被破坏。
- 跨模型回放时不转发 `providerMetadata` 和 `callProviderMetadata`；同模型时保留 text/reasoning/tool call 的 provider metadata。
- completed tool 的 compacted 输出替换为 `[Old tool result content cleared]`；未 compacted 时按 `toolOutputMaxChars` 截断。
- pending/running tool 转成 error tool result，错误文本为 `[Tool execution was interrupted]`，避免 provider 收到悬空 tool_use。
- error tool 若 `state.metadata.interrupted === true` 且有 string output，则按可用输出回放；否则按 error result 回放。
- provider 不支持 tool result media 时，把 media 提取为新的 synthetic user message，首个 text 为 `Attached media from tool result:`，后接 file parts。
- `supportsMediaInToolResult` 是 provider 规则表：Anthropic/OpenAI/Google Vertex Anthropic 支持；Bedrock 和 xAI 仅 image；Google 仅 Gemini 3 且不是 Gemini 2；其他默认不支持。

### 8.13 filterCompacted 重排序算法

`filterCompacted()` 控制送给模型的上下文，不是普通分页过滤。

算法基线：

- 正向扫描消息，记录完成的 compaction：assistant 必须 `summary = true`、`finish` 存在、且无 error，其 `parentID` 标记为完成。
- 遇到已完成的 compaction user message 时读取其 `compaction.tail_start_id`；没有 tail_start_id 则边界之后不再保留旧消息。
- 若存在 tail_start_id，则继续扫描直到该 message id，表示需要保留的最近尾部起点。
- 扫描结果反转后，查找最后一个带 `tail_start_id` 的 compaction user、其后对应 summary assistant、以及 tail_start_id 对应位置。
- 成功时最终顺序必须是 `[compaction_user, summary_assistant, ...retained_tail..., ...newer_messages]`；这会打破时间顺序，因此后续 `latest()` 必须按 monotonic message id 而不是数组位置判断最近 user/assistant/finished。

### 8.14 fromError 映射表

`MessageV2.fromError()` 必须 1:1 映射异常，否则 retry、compaction 和 UI 展示会漂移。

| 输入错误 | 输出错误 |
|---|---|
| `DOMException` 且 name 为 `AbortError` | `AbortedError { message }`。 |
| `OutputLengthError` | 原样返回。 |
| `LoadAPIKeyError` | `AuthError { providerID, message }`。 |
| system error `ECONNRESET` | retryable `APIError`，message 为连接被服务端重置，并保留 `code/syscall/message` metadata。 |
| fetch decompression `ZlibError` 且调用上下文已 aborted | `AbortedError`。 |
| fetch decompression `ZlibError` 且未 aborted | retryable `APIError`，message 为响应解压失败，并保留 code/message。 |
| `ProviderHeaderTimeoutError` | retryable `APIError`，metadata 含 `code` 和 `timeoutMs`。 |
| `APICallError` 被 `ProviderError.parseAPICallError()` 判定为 overflow | `ContextOverflowError { message, responseBody? }`。 |
| 其他 `APICallError` | `APIError { message, statusCode?, isRetryable, responseHeaders?, responseBody?, metadata? }`。 |
| 普通 `Error` | `Unknown { message }`。 |
| 非 Error stream payload 可被 `parseStreamError()` 解析为 overflow | `ContextOverflowError`。 |
| 非 Error stream payload 可被 `parseStreamError()` 解析为 API error | `APIError`，保留 retryable 和 responseBody。 |

### 8.15 Processor 流式事件处理

`session/processor.ts` 将 LLM stream event 落到 message/part，是 agent loop 的状态机核心。

事件类型基线：

| 事件 | 行为 |
|---|---|
| `reasoning-start` / `reasoning-delta` / `reasoning-end` | 创建 reasoning part、增量追加 text、结束时补 `time.end` 并写入 metadata。 |
| `tool-input-start` / `tool-input-delta` / `tool-input-end` | 创建或确认 pending tool；delta 当前丢弃；summary assistant 禁止 tool。 |
| `tool-call` | 将 tool 置为 running，记录 input/provider metadata，执行 doom-loop 检测和 permission。 |
| `tool-result` | 标准化 output/title/metadata/attachments，图片附件先走 `Image.normalize()`，成功后 complete tool。 |
| `tool-error` | 发布失败事件并把 running tool 置为 error。 |
| `provider-error` | 抛出错误进入 retry/halt。 |
| `step-start` | 确保 snapshot，写 `step-start` part。 |
| `step-finish` | 结束 reasoning、聚合 usage/cost/tokens、写 `step-finish`、snapshot patch part、触发 summary，并按 overflow 判定设置 `needsCompaction`。 |
| `text-start` / `text-delta` / `text-end` | 创建 text part、增量写入、触发 `experimental.text.complete`、补 `time.end`。 |
| `finish` | no-op，等待 cleanup 完成 assistant。 |

cleanup 基线：

- 若还有 snapshot，计算 patch 并写 `patch` part。
- 未结束 text/reasoning 要补 `time.end`。
- pending/running tool 先等待 250ms grace；仍未完成则改成 error，`metadata.interrupted = true`，error 为 `Tool execution aborted`。
- 最后设置 `assistantMessage.time.completed` 并更新 message。

`process()` 返回值驱动主循环：`needsCompaction` 为 true 返回 `compact`；被 permission/question 拒绝或 assistant 有 error 返回 `stop`；否则返回 `continue`。provider 错误先经过 retry policy；context overflow 不进入普通 retry，而设置 compaction。

### 8.16 User Message Schema 基线

`MessageV2.User` 字段基线（与 Assistant §8.11 对称）：

| 字段 | 类型 / 语义 |
|---|---|
| `id` | `MessageID` (branded)。 |
| `sessionID` | `SessionID` (branded)。 |
| `role` | 固定 `"user"`。 |
| `time` | `{ created: NonNegativeInt }`；User message 只有创建时间，无 completed。 |
| `format?` | `OutputFormat` union：`{ type: "text" }` 或 `{ type: "json_schema", schema: JSONSchema, retryCount?: NonNegativeInt(default 2) }`。 |
| `summary?` | `{ title?, body?, diffs: FileDiff[] }`；compaction 时可选摘要附加。 |
| `agent` | 当前 agent name。 |
| `model` | `{ providerID, modelID, variant? }`；标识本轮请求使用的模型。 |
| `system?` | 快照当前 system prompt 全文（调试 / 回溯用）。 |
| `tools?` | `Record<string, boolean>`；快照当前 tool 可见性状态。 |

User message 的 parts 使用与 Assistant 相同的 `MessageV2.Part` 12 种 tagged union，但实际生成时只产出 `text`、`file`、`subtask` 等用户侧 part。

### 8.17 Tool Call Repair（experimental_repairToolCall）

AI SDK runtime 使用 `experimental_repairToolCall` 回调实现模型 tool call 自修复：

1. **大小写修复**：将 `toolName` 转为 lowercase，若在 tool registry 中命中则返回修正后的 tool call（toolName 替换为 lowercase）。
2. **无效 fallback**：若大小写修复不命中，将整个原始 tool call 重写为 `toolName = "invalid"`，`input` 为 JSON `{ tool: <original_name>, error: <error_message> }`。

该机制确保 LLM 返回的 tool name 拼写/大小写错误不会直接终止 session，而是走 `invalid` tool 返回错误信息给模型、让模型有机会重试。Rust 实现必须在 AI SDK adapter 层保留此双阶段修复语义，且修复日志需写入 trace。

### 8.18 Session Title 生成

默认 title 格式：`{prefix}{ISO date}`。prefix 常量：

- `parentTitlePrefix = "New session - "`
- `childTitlePrefix = "Child session - "`

`isDefaultTitle()` 使用正则 `^(New session - |Child session - )\d{4}-\d{2}-\d{2}T...Z$` 判断是否为自动生成 title。当 session 收到第一条非 synthetic user message 且 title 仍为 default 时，异步触发 `title` agent 生成摘要 title（只触发一次）。

### 8.19 Agent Loop 退出条件

`runLoop`（`prompt.ts`）退出条件：

1. `process()` 返回 `stop`：permission/question 拒绝或 assistant 有 error。
2. `process()` 返回 `compact`：进入 compaction 流程（见 §8.20）。
3. **正常完成退出**：最后一个 assistant message 的 `finish` 不是 `"tool-calls"` **且** 不存在非 orphaned tool parts **且** `lastUser.id < lastAssistant.id`。"Orphaned interrupted tool"（`metadata.interrupted = true` 且为 error 状态）不阻止退出。
4. `agent.steps` 达到上限时注入 `MAX_STEPS` assistant prefill 后继续一轮（模型不再调 tool → 满足条件 3 退出）。

### 8.20 Overflow Compaction 三阶段算法

当 `processor.process()` 返回 `compact` 且 `overflow = true`（context overflow mid-stream，即 `!handle.message.finish`）时：

1. **寻找 replay message**：找到最后一条非 compaction user message 作为 replay target。
2. **strip media**：把 replay message 中的 media 附件替换为 `[Attached <mime>: <filename>]` 文本描述。
3. **compaction + re-queue**：运行 compaction（summary agent），完成后将 stripped replay message 重新加入消息队列继续执行。

若 replay message 不存在（极端情况），注入 "attachments too large" auto-continue synthetic message 代替。

`overflow` flag 传入 `compaction.create()`，决定是否走三阶段路径。非 overflow 的 compaction（`overflow = false`）走普通 summary + tail 流程。
