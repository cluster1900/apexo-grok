# Storage、Sync 与 Share 开发设计

## 1. 目标与非目标

- 目标：迁移 SQLite schema、JSON migration、data migration state、sync event store/replay/history、session share/share-next。
- 非目标：云端 share 页面 UI 和 provider usage 计算。

## 2. 背景

上游入口：`storage/*`、`sync/*`、`share/*`、`data-migration.ts`、`migration/*`。

## 3. 领域模型

| 聚合/对象 | 说明 |
|---|---|
| `StorageSchema` | project/workspace/session/message/part/todo/account/share/event tables。 |
| `SyncAggregateHistory` | aggregate id、seq、event data、schema version。 |
| `SharedSession` | share id、secret、url、policy、remote sync state。 |
| `DataMigration` | migration id、state、progress、rollback metadata。 |

## 4. 用例编排

- startup -> migrate JSON/SQLite -> report desktop migration progress -> open repository。
- append event -> validate seq -> store -> projectors idempotent update。
- share/unshare -> policy check -> local row -> remote sync -> session updated。

## 5. 关键边界

- `StorageConnection`、`MigrationRunner`、`SyncEventStore`、`ShareRemotePort`、`ProjectorRegistry`。

## 6. 错误模型

`MigrationFailed`、`SchemaDrift`、`SyncSequenceConflict`、`SharePolicyDenied`、`RemoteShareFailed`、`StorageLocked`。

## 7. 测试与验收

- schema snapshot、json migration、workspace-time migration、sync replay/idempotency、share-next contract。

## 8. 上游细节基线（2026-05-27 回补）

### 8.1 Data Migration

`session_usage_from_messages` 是当前上游显式 data migration：分页读取 session，每页 100 个；从 assistant message 的 JSON data 聚合 `cost`、`tokens.input`、`tokens.output`、`tokens.reasoning`、`tokens.cache.read`、`tokens.cache.write`；写回 session 表并保持 `time_updated` 不变。migration 在 background fiber 中运行，完成后写 `data_migration` 表，失败只记录日志不阻塞启动。

### 8.2 Sync 操作

Sync HTTP/API 至少包含 `start`、`replay`、`steal`、`history`：

- `start`：启动 workspace sync。
- `replay`：校验完整事件历史并按 seq 重放。
- `steal`：转移 session/aggregate owner，用于 session 所有权迁移。
- `history`：按客户端已知 aggregate seq 返回增量历史。

`history` 请求 payload：`HistoryPayload = Record<aggregateID: string, knownSeq: NonNegativeInt>`——客户端告知服务端每个 aggregate 已知到哪个 seq。服务端查询规则为 `NOT (aggregate_id = id AND seq <= knownSeq)` 对所有条目取反，即返回客户端尚未拥有的所有事件。

`replayAll` 要求所有事件属于同一 aggregate 且 seq 连续；owner 不匹配时跳过。`EventSequenceTable` 使用 **upsert**（`onConflictDoUpdate` on `aggregate_id`）同时更新 `seq` 和 `owner_id`，不是 insert——Rust 版必须用 `INSERT ... ON CONFLICT DO UPDATE` 语义，否则已有序列行的 replay 会失败。

### 8.3 Share Next / Legacy

上游同时存在 legacy share API 和 `share-next`。`share-next` 支持 account/org token、console API `/api/shares`、legacy API `/api/share` fallback、local `SessionShareTable`、queued sync、session/message/part/session_diff/model 数据同步。策略基线：`disabled` 禁止分享；`auto` 或 `RuntimeFlags.autoShare` 自动分享非 fork/root session；manual 通过显式 share API 触发。

### 8.4 SQLite 平台适配

storage 有 `db.bun.ts`、`db.node.ts`、`db.ts` 三层适配。Rust 迁移要保留 channel database 路径策略：`latest/beta/prod` 或 `disableChannelDb` 使用 `opencode.db`，其他 channel 使用 `opencode-{channel}.db`；支持 `OPENCODE_DB` 覆盖、`:memory:`、WAL、busy timeout、migration journal。

### 8.5 SessionMessage V2 Projector

上游存在两套消息 projection：legacy `message` / `part` 表，以及 `projectors-next.ts` 维护的 `SessionMessageTable`。Rust 迁移不能只实现 legacy 表。

`SessionMessageTable` 用于 v2 SDK/Desktop 的 session message 展示，按 session id、message id、type、time_created 和 JSON data 存储归一化消息。`projectors-next` 从 EventV2 / SessionEvent 增量维护该表，覆盖：

- agent/model switched。
- prompted/synthetic message。
- shell started/ended。
- assistant step started/ended/failed。
- text/reasoning started/ended。
- tool input started/ended、tool called/success/failed。
- retry、compaction started/ended。

projection 必须幂等，delta event 可跳过但不能破坏状态。实现阶段需要保留 dual-write/dual-projector 兼容策略，直到 legacy API、SDK 和 Desktop 全部切到 `SessionMessageTable`。
